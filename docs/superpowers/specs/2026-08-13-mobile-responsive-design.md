# 集团仓库管理系统手机端响应式适配设计

## 1. 背景与目标

现有系统是 React 网页应用，电脑端承担完整仓库业务。此次不新建独立手机 App，也不建立独立的 `/mobile` 子系统，而是在同一套页面、接口、权限和业务规则上增加手机端响应式呈现。

手机端的核心目标是让仓库管理员在企业微信内置浏览器中高效完成：

- 库存、物品、仓库和批次查询；
- 实时业务通知与任务跳转；
- 单物品、单批次的日常入库；
- 已审批出库单的完整办理，包括多物品、跨仓库、跨批次分配、少出或零出说明；
- 待出库单取消等少量边界明确、可二次确认的操作。

电脑端继续作为完整操作端。调拨、盘点、月结、主数据维护以及异常情况下的复杂处置默认留在电脑端。

## 2. 已确认的产品决策

### 2.1 入口与导航

库存管理员手机端采用任务导向的五项底部导航：

1. 首页；
2. 查询；
3. 入库；
4. 出库；
5. 更多。

“更多”展示当前用户与登录信息，以及只能在电脑端完成的能力说明，不把电脑端全部侧边栏菜单机械搬到手机端。

财务角色不显示入库、出库等无权限入口，使用“首页、查询、报表、更多”四项导航；申请人沿用现有“暂无后台权限”边界，不进入仓库后台。导航只根据服务端会话角色和权限结果生成，不能仅靠 CSS 隐藏越权入口。

底部导航与正文使用同一套 Lucide 线性图标语言。图标基准尺寸约为 `18px`，底部标签约为 `12px`，正文操作标签约为 `13px`；二者视觉重量接近，避免底部导航压过正文。所有主要触控目标不小于 `44px × 44px`。

### 2.2 手机首页

首页沿用现有仓库系统的深蓝、橙色和中性灰设计语言，采用已确认的统一层级版：

- 顶部显示仓库选择、问候与当前角色；
- 其下提供物品、仓库或批次统一搜索；
- 入库、出库放在同一个白色快捷操作面板中，以小尺寸橙色和深蓝图标区分；
- “今日概览”使用紧凑指标条展示待出库、低库存、库存品类和通知；
- 只在需要时显示轻量提醒，不使用大面积高饱和卡片；
- 卡片统一采用约 `10px–12px` 圆角、浅边框和轻阴影。

顶部栏、正文快捷操作和底部导航构成三个清楚但不过度竞争的层级。长仓库名称必须截断或换行，不得挤出窄屏。

### 2.3 查询

查询入口使用应用内语义路由 `/admin/inventory`，不建立 `/mobile` 路由。它与顶部全局搜索共享现有库存检索数据源；桌面端也能打开同一查询页，手机端结果使用卡片而不是横向滚动表格。页面提供统一搜索和筛选，可按物品编码、名称、规格、分类、仓库和批次号检索，卡片至少显示：

- 物品编码和名称；
- 仓库；
- 批次；
- 剩余数量；
- 采购单价和金额（仅现有管理员、财务角色可见）。

申请人等无价格权限角色不接收或不展示采购单价与金额。点击结果进入同一页面内的库存或批次详情，不复制一套独立数据源。

### 2.4 手机入库：单页分组式

手机端入库采用单页分组表单，不使用多步向导。一次只录入一个物品、一个批次，页面分为：

- 仓库与物品；
- 批次与采购信息；
- 数量、单价和预计金额；
- 提交确认。

预计金额由数量和单价使用精确十进制规则计算，只作为预览；最终入库结果以服务端为准。提交成功后可保留仓库、采购日期和采购人，便于连续录入；物品、批次、数量、单价等业务数据清空。失败时保留用户输入并将错误定位到对应字段。

### 2.5 手机出库：四步引导式

手机端出库使用四步引导流程：

1. 选择待出库审批单；
2. 为每个审批物品分配仓库、批次和数量，可新增多条分配以支持跨仓库、跨批次；
3. 填写少出或零出原因并复核审批数量、实际数量、差额和金额；
4. 二次确认后提交并展示完成结果。

沿用现有业务规则：审批通过不预占库存，实际数量不能超过审批数量，少出或零出必须填写原因，一张审批单只能结案一次，出库金额由批次采购价决定。

流程中的所有步骤共享一个出库状态对象，前进和返回不会丢失已选分配。提交前重新拉取并校验可用库存；如库存发生变化，停留在复核步骤，标记失效批次并保留其他有效输入，由用户重新选择后再提交。

“取消待出库单”不混入正常四步流程，作为独立危险操作：必须填写原因、二次确认，并由服务端继续执行权限与状态校验。

### 2.6 通知与任务中心

手机端通知是实时任务入口，不建立永久“已读”账本：

- 待出库任务跳转到四步出库流程；
- 低库存跳转到对应库存查询；
- 盘点、月结和复杂异常可查看摘要，并明确提示前往电脑端处理；
- 当底层业务状态已解决，任务自动从列表消失。

通知不引入 WebSocket 或永久已读状态。任务列表在应用进入、通知中心打开、页面重新变为可见以及入库、出库或取消成功后立即刷新；通知中心保持打开时每 30 秒轮询一次，关闭后停止轮询。待出库链接使用可渲染的 `/admin/outbound` 入口，低库存链接携带物品检索条件进入 `/admin/inventory`，不使用当前无法直接渲染的伪子路由。

通知弹层或抽屉必须适配窄屏，不使用依赖 hover 的交互，也不能超出视口。

## 3. 技术架构与边界

### 3.1 同源响应式架构

采用“共享业务与数据逻辑 + 响应式呈现层”方案：

- 保留同一 React 应用、现有 URL、API 和认证；
- 桌面页面继续呈现完整操作能力；
- 在窄屏下由 `MobileShell` 提供顶部区域、底部导航、安全区和移动任务入口；
- 查询结果、复杂表格和业务表单使用移动卡片或移动专用呈现组件；
- 数据请求、校验、金额规则、权限判断和提交动作下沉到共享 hook 或纯函数接缝，桌面与手机共同使用。

响应式断点以现有 `820px` 为边界：视口宽度小于或等于 `820px` 使用移动呈现，大于 `820px` 使用桌面呈现。纯布局差异优先用 CSS 媒体查询；会产生不同交互树、焦点管理或请求副作用的组件使用统一的 `matchMedia` 响应式 hook，确保同一时刻只挂载一套可交互表单，避免重复请求、重复 `id` 和隐藏表单误提交。跨断点切换时，业务状态保存在共享父级状态或草稿接缝中，不因呈现组件卸载而静默丢失。

### 3.2 页面与能力边界

手机端不复制调拨、盘点、月结和主数据维护表单。相关入口只展示摘要、状态和“请在电脑端处理”的明确说明。桌面端现有路由和交互不因移动适配而降级。

服务端继续作为库存、价格、权限和业务状态的唯一权威。移动端不得通过隐藏按钮代替服务端权限控制，也不新增绕过现有业务服务的快捷接口。

### 3.3 共享数据流

- 仓库上下文、统一检索、库存与批次详情复用现有数据源；
- 入库使用现有入库业务服务，只增加适合移动呈现的状态与校验接缝；
- 出库待办、可用批次、确认和取消复用现有服务及事务边界；
- 通知由库存和业务状态实时聚合，跳转到同一业务实体；
- 金额使用项目既有精确十进制实现，禁止依赖 JavaScript 浮点结果作为最终值。

## 4. 草稿、校验与错误恢复

### 4.1 会话草稿

入库与出库草稿只保存在 `sessionStorage`，不新增服务器草稿或跨设备同步。键名必须包含版本、用户标识和业务类型；出库草稿还应包含审批单标识。规则如下：

- 刷新或临时离开页面后可恢复；
- 成功提交、明确放弃或取消对应业务后清除；
- 登录用户变化时不得自动加载上一用户草稿；
- 标准物品、仓库或批次已失效时保留其余输入，但要求重新选择失效项；
- 草稿不保存认证凭证或生产 Secret。

### 4.2 校验与提交

- 必填项、数量范围、分配合计和少出原因在前端即时校验；
- 服务端重复执行权限、状态、库存余额、批次归属和一次性结案校验；
- 提交按钮具有加载态并防止重复提交；
- 入库、出库和取消操作在最终提交前展示清晰的二次确认摘要；
- 网络失败保留草稿并允许重试；业务错误定位到字段或分配行；会话失效时引导重新登录，登录后仍需核对草稿所属用户。

### 4.3 界面状态

查询、待办和表单分别提供可区分的加载、空数据、错误和成功状态。弹窗与抽屉打开后锁定背景滚动、移动焦点并支持返回或 Escape；关闭后焦点回到触发控件。软键盘弹出时，当前输入、错误提示和主要操作不得被底部导航遮挡。

## 5. 企业微信与无障碍适配

- 页面高度优先使用 `100dvh`，并提供 `100vh` 回退；
- 底部导航和固定操作区适配 `env(safe-area-inset-bottom)`；
- 表单控件使用足以避免 iOS/WebView 自动缩放的字号；
- 在 `320×568` 窄屏下不得出现页面级横向滚动；
- 触控目标不小于 `44px`，焦点样式清晰，状态不只依赖颜色；
- 不使用 hover-only 操作；
- 验证企业微信内置浏览器中的返回键、软键盘、滚动锁、弹层和底部导航行为。

## 6. 可测试接缝与 TDD 策略

实现按“失败测试 → 最小实现 → 通过 → 重构”推进，优先建立以下接缝：

### 6.1 纯函数与组件测试

- 响应式导航配置和能力可见性；
- `820px` 边界两侧只挂载一套交互树，跨断点不丢失草稿；
- 入库预计金额与字段校验；
- 出库分配合计、差额、少出或零出原因规则；
- 会话草稿版本、用户隔离、恢复和清理；
- 库存变化后失效分配标记与状态保留；
- 价格和金额的角色可见性。

### 6.2 API 与服务集成测试

- 手机端使用的库存、仓库和批次查询结果及权限裁剪；
- 完整出库、跨仓库/跨批次、部分出库、零出库；
- 待出库取消、重复提交、并发库存变化；
- 无权限、会话失效和明确业务错误；
- 入库提交与服务端金额、库存结果一致。

### 6.3 移动端端到端测试

Playwright 覆盖：

- 首页、仓库切换、统一查询和批次详情；
- 单页分组入库及成功后的字段保留规则；
- 四步出库、返回编辑、二次确认和成功结案；
- 草稿刷新恢复与主动放弃；
- 通知跳转和任务自动消失；
- 管理员与财务导航差异及越权入口不可见；
- 抽屉、弹窗、软键盘相关滚动和窄屏溢出；
- 桌面端关键业务回归。

视口至少包含 `320×568`、`390×844`、`430×932`、`820px` 边界，以及一个现有桌面视口。复杂业务在手机端必须转为卡片或分组表单，不以横向滚动表格作为完成路径。

## 7. Git、安全与交付策略

- 原始 `feat/warehouse-system@270d7f8` 工作树及其 13 个未提交文件保持原样，不清理、不覆盖；
- 从干净的生产部署基线 `codex/production-deployment@5f17963` 创建隔离分支 `codex/mobile-responsive`；
- 不把旧版 `item-service.ts` 或 `server.ts` 覆盖到生产基线；
- 仅在隔离分支实现和验证，不直接部署服务器；
- 不读取、修改、提交或输出任何生产 Secret，不连接生产数据库；
- 完成本地实现、验证和评审后，由用户决定如何整合与发布；
- 最终把 `PROJECT_STATUS.md` 带入隔离分支并更新手机端范围、Git 基线、验证结果和“尚未部署”状态。

## 8. 验收标准

1. 手机端五项底部导航、首页和统一视觉层级在 320px 至 820px 范围内协调，无页面级横向溢出。
2. 底部导航与正文图标、文字的尺寸和重量接近，主要触控目标满足 44px。
3. 管理员可在手机完成单物品单批次入库及完整的多物品、多仓库、多批次出库。
4. 少出、零出、库存变化、重复提交和取消待办均得到前后端一致校验及可恢复反馈。
5. 库存、物品、仓库、批次与通知能在手机高效查询和跳转，价格信息严格按现有角色权限显示。
6. 管理员显示五项任务导航；财务只显示首页、查询、报表、更多；申请人不能进入仓库后台。
7. 调拨、盘点、月结和主数据维护在手机端明确引导到电脑端，桌面完整操作不退化。
8. 企业微信内置浏览器的安全区、动态视口、软键盘、返回、弹层和滚动锁通过验证。
9. 针对性单元/集成/E2E 测试、全量测试、类型检查、构建与 `git diff --check` 均以新鲜输出通过；若本机 Docker 环境仍不可用，Docker 相关验证必须明确记录为环境阻塞，不得伪称通过。
10. `PROJECT_STATUS.md` 准确记录实现范围、生产基线、验证证据和未部署状态。

## 9. 明确不在本次范围

- 独立原生 App、小程序或另一套移动前端；
- 服务端或跨设备草稿；
- 手机端调拨、盘点、月结和主数据维护；
- 改造企业微信审批流程或登录体系；
- 改动生产 Secret、直接连接生产数据库或直接发布到服务器；
- 与移动适配无关的生产部署重构。
