# 出库确认闭环设计

## 目标

让管理员能够从企业微信审批生成的待出库单中，选择实际出库仓库、入库批次和实际数量，完成一次性出库结案，并将校验后的结果写入库存流水。

## 已确认的业务规则

- 审批入口继续使用企业微信，库存后台只处理已通过且待出库的审批单。
- 管理员在实际出库时选择仓库、批次和数量；审批通过不预占库存。
- 实际出库数量不能超过审批数量，可以少出，但少出或零出必须填写原因。
- 一张审批单可以包含多行物品；同一物品可以拆分到多个仓库或入库批次。
- 出库金额按所选入库批次的采购单价计算，不允许管理员另填出库单价。
- 一张审批单只允许确认一次；部分出库或零出库结案后不得补出，后续需要重新发起审批。
- 领用人无需在后台确认；管理员确认出库即视为业务完成。
- 出库失败时不写入库存流水；错误信息显示在当前审批单编辑区域。

## 页面设计

待出库页面继续使用审批单列表。每条审批单提供“办理出库”操作，点击后展开详情编辑区：

1. 每个审批行展示物品、审批数量、已填写实际数量和差额。
2. 每个审批行至少有一条分配行，管理员选择仓库、批次和数量。
3. 分配行可新增和删除，以支持跨仓库、跨批次出库。
4. 批次选择只展示对应物品且仍有库存的批次，自动带出仓库、剩余库存、采购单价和金额。
5. 页面显示审批总数量、实际总数量、总金额和少出原因输入框。
6. “确认出库”提交当前审批单；实际数量为零时也允许提交，但原因必填。
7. 成功后显示结果并刷新待出库列表；失败时保留用户填写内容并显示错误。

## 接口设计

在现有出库服务上增加待出库单可用批次查询能力：

- `GET /admin/outbound/pending`：保留现有待出库列表。
- `GET /admin/outbound/:approvalId/options`：返回该审批单各物品可用的批次，包含 `batchId`、`warehouseId`、`itemId`、`remainingQuantity`、`unitCost`。
- `POST /admin/outbound/confirm`：沿用现有请求结构 `{ approvalId, allocations, reason? }`，由服务层统一执行数量、批次归属、库存余额、少出原因和一次性结案校验。

前端不自行计算或信任金额，金额展示可以预览，但最终金额以服务层按批次采购单价计算的结果为准。

## 错误处理

- 审批单不存在、已结案、审批行不存在、批次不存在或批次不属于所选仓库时，显示明确错误。
- 实际数量超过审批数量或批次余额不足时，阻止提交并显示对应原因。
- 少出或零出没有原因时，前端立即提示，服务端继续强制校验。
- 确认请求失败不刷新列表，不清空编辑内容。

## 测试验收

- 服务层覆盖完整出库、部分出库、零出库、超审批数量、批次余额不足和重复确认。
- 路由层覆盖管理员认证、可用批次查询和确认请求的数据传递。
- 前端端到端测试覆盖展开审批单、填写分配、成功确认和错误提示。
- 类型检查、构建和全量测试通过。
