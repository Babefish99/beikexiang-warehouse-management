# 审批意向与标准物品出库设计

## 状态

已于 2026-09-04 完成业务设计确认，等待书面规格评审。

本设计取代《2026-08-08 出库确认闭环设计》中“企业微信审批行已经绑定标准物品”“整单共用少出原因”以及相应接口结构。原设计中的不预占库存、按采购批次成本计价、一次性结案、服务端校验和失败不写库存等规则继续有效。

## 背景与问题

现有审批同步在导入审批时就要求把审批物品解析成一个标准物品，并将 ApprovalLine.itemId 设为必填。办理出库时，可用仓库和批次只按这个物品查询。

当审批行绑定的是 item-0001 等占位物品，而实际库存属于其他标准物品时，后端返回空批次，页面便只显示“选择仓库”和“选择批次”，管理员无法继续。直接修改审批行的物品绑定会覆盖审批原文，不能满足审计要求。

## 目标

- 申请人可以在企业微信填写大概的物品名称，一张审批单最多包含五项物品。
- 仓库管理员在企业微信完成审批后，在仓库系统为每项意向手动确认一个具体标准物品。
- 审批原文、管理员的出库决定和最终库存扣减彼此分离并可追溯。
- 一个审批意向只能选择一个标准物品，但该物品可以跨多个仓库和采购批次出库。
- 兼容能够安全办理的旧审批，并明确阻止占位物品或缺少单位的旧审批出库。

## 非目标

- 不在企业微信中维护或展示标准物品下拉。
- 不根据意向名称自动绑定标准物品。
- 不把仓库系统选择结果回写企业微信审批表单。
- 不允许管理员更改审批数量或审批单位。
- 不在本次改造中增加预占库存、分次结案或自动退库。
- 不通过手工修改生产数据库来修复旧审批。

## 方案选择

已比较并确认三种方案：

1. 管理员选品后覆盖 ApprovalLine.itemId：改动较少，但会改变审批原始含义，审计不可接受。
2. 审批意向与出库决定分开：保留不可变审批原文，以独立出库决定记录标准物品和实际数量。本设计采用此方案。
3. 继续使用占位物品并维护映射：迁移较轻，但占位物品会继续污染库存语义并产生空批次等故障。

选择方案二是因为它把企业微信输入、管理员业务判断和库存扣减放在三个清晰的模块中，后续修改候选排序或批次分配时不需要改写审批数据。

## 术语与核心关系

领域术语以仓库根目录的 CONTEXT.md 为准。

~~~mermaid
flowchart LR
    A[企业微信审批意向行<br/>原文/数量/单位/备注] -->|审批通过并同步| B[不可变审批意向行]
    B -->|管理员逐项办理| C[出库决定行<br/>标准物品/实际总量/差异原因]
    C -->|实际数量大于 0| D1[批次分配行<br/>仓库 A / 批次 1 / 数量]
    C -->|可以有多条| D2[批次分配行<br/>仓库 B / 批次 2 / 数量]
    D1 --> E[原子校验并扣减库存]
    D2 --> E
    C -->|实际数量为 0、原因必填| F[零出库结案<br/>不选物品、不扣库存]
~~~

关系约束：

- 一张审批单包含一至五条审批意向行。
- 一条审批意向行在结案时恰好产生一条出库决定行。
- 一条正数出库决定必须选择一个标准物品，并包含一条或多条批次分配。
- 一条零出库决定不选择标准物品，也不包含批次分配。
- 同一出库决定的所有批次分配必须属于同一个标准物品。

## 企业微信审批模板

新模板名称为“仓库物品领用申请”。

表单字段：

1. 用途：必填，多行文本。
2. 物品明细：可重复添加，最少一项、最多五项。
3. 每项包含：
   - 意向物品名称：必填文本；
   - 审批数量：必填正整数；
   - 单位：必填手工文本；
   - 补充要求：选填文本。

审批流程：

1. 申请人提交。
2. 集团领导审批。
3. 仓库管理员审批。
4. 全部通过后在企业微信中抄送赵婉婉。
5. 仓库系统通过回调或主动同步导入已通过审批。

企业微信中的管理员节点只负责同意或驳回。具体标准物品、仓库、批次和实际数量只在仓库系统办理。赵婉婉收到企业微信抄送时看到的是已批准申请；仓库系统不额外发送出库完成消息。

## 数据模型

### ApprovalLine：审批意向行

保留现有模型名称以降低迁移范围，但改变其领域含义：

- requestedItemName：申请人填写的意向物品名称，必填。
- requestedQuantity：审批数量，数据库继续使用现有 Decimal 存储，写入时必须为正整数。
- unit：申请人手填的审批单位，必填。
- note：申请人填写的补充要求，可空。
- itemId：改为可空，只表示旧式确定物品审批的历史绑定；新模板审批不写该字段。
- legacyResolutionStatus：记录旧审批是否可以按锁定物品继续办理。取值为 NOT_APPLICABLE、EXACT_LOCKED 或 REAPPLY_REQUIRED。

同步成功后，上述审批原文字段不可由出库流程修改。

ApprovalRequest 新增 sourceTemplateId，用于选择解析器和审计新旧模板来源。迁移得到但尚无模板 ID 的记录保持为空，必须经企业微信重新同步后才能判定旧单兼容性。

### OutboundDecisionLine：出库决定行

新增模型，至少包含：

- outboundOrderId
- approvalLineId，全局唯一，保证一条审批意向只办理一次
- selectedItemId，正数出库必填，零出库为空
- actualQuantity，非负整数，由服务端汇总批次分配得到
- varianceReason，实际数量小于审批数量时必填
- decidedBy
- decidedAt

### OutboundAllocation：批次分配行

批次分配改为从属于出库决定行，同时保留仓库、标准物品、采购批次、数量、单位成本、金额及退库所需的原始数量。服务端从采购批次验证标准物品和仓库，不信任客户端单独提交的对应关系。

OutboundOrder.reason 只为旧数据保留；新流程使用每条 OutboundDecisionLine.varianceReason。

### 迁移

- 将 ApprovalLine.itemId 改为可空，历史值保持不变。
- 新模板审批行的 legacyResolutionStatus 为 NOT_APPLICABLE。
- 旧审批只有在重新同步后能够证明其来自确定物品选择控件、选择项仍映射到同一个启用的标准物品、审批单位与物品单位一致，并且审批数量为正整数时，才标记 EXACT_LOCKED。
- 旧固定文本模板、占位或联调物品、映射不一致、模板来源不明、无法重新同步以及单位缺失的记录一律标记 REAPPLY_REQUIRED。系统不得根据名称相似度猜测旧单资格。
- 为已有已完成出库数据按审批行回填出库决定行，再把相应批次分配关联到决定行。办理人与时间取自原出库单；存在整单少出原因时，将原原因复制到对应的历史少出决定行。
- 迁移不得改变任何库存余额、批次数量、库存流水或历史金额。
- 数据库继续使用 Decimal 以兼容既有数据；新审批和出库接口在领域层强制整数规则，不扩大为全系统数量类型变更。

## 同步与状态流转

~~~mermaid
stateDiagram-v2
    [*] --> 企业微信审批中
    企业微信审批中 --> 已驳回: 任一审批人驳回
    企业微信审批中 --> 待出库: 集团领导与仓库管理员均通过
    待出库 --> 已取消: 实际出库前撤销审批
    待出库 --> 已完成: 每项全部出库
    待出库 --> 部分出库: 至少一项少出或零出
    待出库 --> 不可供应: 所有项均零出库
    已完成 --> 撤销异常: 出库后发现审批撤销
    部分出库 --> 撤销异常: 出库后发现审批撤销
    不可供应 --> 撤销异常: 结案后发现审批撤销
~~~

- 企业微信回调和主动同步都走同一个幂等同步模块。
- 只有集团领导和仓库管理员均已通过的审批才进入待出库列表。
- 新模板解析器保存原始意向，不查询或绑定标准物品。
- 同一审批编号重复同步时更新审批状态，不重复创建审批行或待出库记录。
- 模板字段缺失、物品超过五项、数量不是正整数或单位为空时，不生成可办理记录，并写入可见的同步异常。
- 审批在出库前撤销时标记已取消；结案后发现撤销时标记撤销异常并告警，不自动回补库存，后续按正式退库流程处理。

## 标准物品候选规则

- 意向物品名称只用于候选排序和默认搜索词，不自动产生绑定。
- 候选只包含启用、审批单位一致且当前总可用库存大于零的标准物品。
- 管理员可以清空意向搜索词，查看所有符合单位与库存条件的标准物品。
- 单位比较只执行去除首尾空白和全角/半角规范化，不做语义换算或单位别名映射。
- 管理员不能修改审批单位；无法匹配时必须驳回或重新申请。
- 旧式确定物品审批若绑定真实有效的标准物品且单位明确，候选物品固定且不可更换。
- 只有 legacyResolutionStatus 为 EXACT_LOCKED 的旧式确定物品审批可以办理。
- legacyResolutionStatus 为 REAPPLY_REQUIRED 的旧审批显示“需重新申请”，不能进入批次分配。

## 办理页面

桌面端和移动端采用相同业务规则：

1. 每个审批意向显示一张独立卡片，锁定展示意向名称、审批数量、审批单位和备注。
2. 在仓库与批次之前增加标准物品选择。
3. 选定标准物品后才显示它的可用仓库和采购批次。
4. 每项可以增加多条分配，分别填写仓库、批次和整数数量。
5. 更换标准物品会先提示，再清空该项已有分配。
6. 页面逐项展示审批数量、实际总量和差额。
7. 实际数量小于审批数量时，该项显示并要求填写少出或零出原因。
8. “本项不出库”会清空该项物品与分配，要求填写零出原因，但不影响其他项。
9. 提交前展示“申请意向 → 标准物品 → 仓库/批次 → 实际数量”的逐项复核摘要。
10. 一张审批单一次性结案，结案后不能补出；如需补领必须重新申请。

桌面端当前“申请物品/数量”选择框不再承担物品选择功能。它由审批意向卡片和明确的标准物品选择框替代，从而消除“审批行是 item-0001 时仓库下拉为空”的误导状态。

## 模块与接口

现有出库模块继续提供一个小接口，由实现内部完成候选生成、校验、事务写入和状态计算：

- listPending()：返回待出库审批及不可变审批意向。
- listOptions(approvalId)：按审批行返回符合单位与库存规则的标准物品候选及其可用批次。
- confirm(input)：一次性提交整张审批的逐项出库决定。

confirm 请求概念结构：

~~~ts
{
  approvalId: string;
  decisions: Array<{
    approvalLineId: string;
    selectedItemId?: string;
    allocations: Array<{
      warehouseId: string;
      batchId: string;
      quantity: string;
    }>;
    varianceReason?: string;
  }>;
}
~~~

客户端不提交可信的实际总量、单位成本或金额。服务端从批次分配汇总实际数量，并从采购批次取得标准物品、仓库和单位成本。

## 不变量与错误处理

确认出库必须在同一数据库事务内验证并写入：

- 操作者具有仓库管理员权限。
- 审批存在、已通过且处于待出库状态。
- 请求恰好包含审批的每一条意向行，不能缺失、重复或附加其他审批行。
- 所有审批数量、实际数量和批次分配数量都是整数。
- 正数出库决定恰好选择一个单位一致的标准物品，且至少包含一条正整数分配。
- 零出库决定不包含标准物品和批次分配，且原因必填。
- 每项实际总量不超过审批数量；少出时该项原因必填。
- 每个批次属于声明的仓库和所选标准物品，并有足够可用库存。
- 审批尚未被其他请求结案。

任一校验失败时整张审批不创建出库单、不扣库存、不写流水。前端保留草稿并将错误定位到对应审批意向。库存并发冲突时要求刷新候选后重新复核。

回调、同步和确认均保持幂等。重复确认已结案审批时返回既有结果或明确的已结案响应，不进行第二次库存写入。

## 金额、状态与退库

- 每条分配金额由批次单位成本乘实际数量得到，出库单金额为所有分配金额之和。
- 所有审批意向足额出库时状态为 COMPLETED。
- 至少一项少出或零出但存在正数出库时状态为 PARTIALLY_ISSUED。
- 所有项均零出时状态为 UNAVAILABLE。
- 退库继续基于实际出库的批次分配办理；零出库决定没有可退数量。

## 安全与审计

- 仅仓库管理员可以查询候选和确认出库。
- 审批原文不可由办理接口修改。
- 出库决定记录办理人和时间；批次分配保留批次、成本和金额。
- 不把 Secret、令牌或回调凭据写入代码、日志或设计文档。
- 不通过创建占位库存或修改审批历史绑定来绕过候选规则。

## 测试与验收

### 解析与同步

- 新模板一至五项意向的成功解析。
- 缺字段、超过五项、非正整数数量和空单位的同步异常。
- 回调与主动同步重复执行不产生重复数据。
- 新旧模板并存时按模板 ID 选择正确解析器。
- 审批驳回、撤销和结案后撤销的状态处理。

### 领域与持久化

- 意向名称不触发自动绑定。
- 候选按启用状态、单位和正库存过滤，并按意向名称排序。
- 单位不一致在候选和确认两层都被拒绝。
- 一个标准物品跨仓库和跨批次成功出库。
- 同一审批意向混用两个标准物品被拒绝。
- 小数、负数、超审批数量、库存不足和重复审批行被拒绝。
- 每项少出和零出分别要求原因。
- 所有项零出不创建库存扣减。
- 并发扣减只允许一个事务成功。
- 重复确认不产生第二张出库单或第二组流水。
- 数据迁移前后库存余额、历史金额和退库关系不变。

### 界面

- 桌面端和移动端均先选标准物品，再选仓库和批次。
- 意向名称只影响推荐排序，管理员可以查看所有同单位有库存物品。
- 更换物品清空分配并要求确认。
- 少出原因按审批意向分别填写。
- 零出一项不阻止其他项出库。
- item-0001 或缺单位旧单显示“需重新申请”，不再呈现无内容的仓库下拉。
- 复核页正确展示申请意向、标准物品、各批次和实际总量。
- 服务端失败后保留输入并定位错误。

## 发布与切换

1. 合并数据库迁移、后端、前端和测试；代码同时识别新旧模板。
2. 先部署兼容代码，暂不启用新模板，验证迁移、健康检查和现有功能。
3. 在企业微信创建“仓库物品领用申请”，配置表单、审批人、抄送人、回调和新模板 ID。
4. 发起专用验收审批，走完集团领导、仓库管理员和赵婉婉抄送。
5. 验证审批同步、标准物品候选、单位限制和批次选项，首次验收不执行实际出库。
6. 验收通过后停止发起旧模板并启用新模板。
7. 用正式审批另行验证首次库存扣减；未经明确确认不得代替用户执行实际出库。
8. 监控同步异常、需重新申请旧单、库存冲突和撤销异常。

## 验收标准

- 新审批不需要标准物品编码或精确名称即可通过同步进入待出库列表。
- 管理员能为每项审批意向选择一个单位一致的标准物品，并从该物品的实际库存中分仓、分批出库。
- 审批原文不会因管理员选择而改变，出库决定和库存流水可以逐项追溯。
- 实际数量永远不超过审批数量，所有审批和实际数量均为整数。
- 少出与零出原因准确关联到单项物品。
- 占位物品或缺单位的旧审批不能错误扣减库存，并得到明确的重新申请提示。
- 任何失败或重复请求都不会造成部分写入或重复扣减。
- CI、数据库迁移验证、后端测试、桌面端和移动端端到端测试全部通过后才允许部署。
